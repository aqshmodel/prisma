# 管理統計ダッシュボード運用

## 集計の定義

集計元は `diagnosis_results`。全期間累計は全レコード数（人数ではない）。再診断、識別不能な過去の重複・テストを含む。トップレベルのFirestore TimestampをJSTへ変換する。日時不明・集計基準時刻以降は期間別集計から除き全期間にのみ含む。各分布は当該分類の有効件数を分母とする。全期間モードに比較対象はない。

今月比較は集計時点と同じ前月の日・時刻未満まで。前月にその日がない場合は翌月1日0時未満。完了月は前月全体。記録開始以前の観測や保存障害による欠測は復元できない。0件から未利用と保存失敗を区別できない。月次推移は記録開始月以降。

## APIと構成

- `GET /api/admin/statistics/?period=YYYY-MM|all`: Firebase IDトークンをBearerで送信。全件集計の同一スナップショットからKPI・推移・内訳を返す。
- `GET /api/admin/diagnosis-logs/?period=YYYY-MM|all&cursor=DOCUMENT_ID`: 50件の明細とnextCursor。月指定は日時降順。全期間は日時不明を漏らさないためID順。
- `POST /api/diagnosis-results/`: `{id: UUID, locale: ja|en, result: DiagnosisResult}`。201=新規保存、200=同一再送、409=同一IDで異なる内容、400=不正、503=一時失敗。匿名診断を維持。個人追跡は追加しない。匿名投稿なので正規形式の虚偽投稿を完全には防げない。
- `PRISMA_ADMIN_UIDS`: 管理者UIDのカンマ区切り。未設定は403。既存Firebase管理者ユーザーのUIDを運営者が確認して設定する。メールやユーザー一覧を推測して自動登録しない。
- 既存のFirebase Adminサービスアカウント（またはADC）がサーバーで利用可能なことを確認する。

`_admin_statistics/diagnosis-v1` にgzip/Base64の集計のみ保存。TTL5分、分散ロック120秒、走査予算90秒。500件ずつID順に原本を投影して取得。圧縮後850KBを上限にし、超過時は失敗として前回値を保持する。画面閲覧・更新時だけ更新し、定期ジョブは追加しない。同時更新中に前回値がなければ503と再試行案内。生成時点は走査開始時刻で、走査中の新規書き込み・変更を含む厳密なトランザクションスナップショットではない。過去データの更新がない通常運用では次回走査で一致する。

失敗時は旧payloadを維持して更新失敗と元の集計時刻を返す。認証済みレスポンスは `private, no-store`。一括CSVは集計のみで個別情報は含めない。

## 本番公開前の必須事項

2026-09-22、公開の承認後に移行用ルールを適用済み。旧ルールの全コレクション匿名writeを廃止し、管理者本人の旧admin読み取りと、検証済みの旧診断createのみ残した。原本update/delete、一般利用者のread、集計・注文のクライアントアクセスは禁止。Rules APIの22項目が成功。適用前ルールはローカルの `documents/admin/rules-backups/` に退避した。

1. 現行ルールを退避し、必要な他クライアントがないことを確認する。現行コードのチーム注文等はAdmin SDK経由。
2. `firebase/firestore.transition.rules` をFirebase Emulator/Rules Playgroundで検証する。匿名/一般ユーザーの原本read/update/delete、集計read/write、注文read/writeを拒否すること、旧形式の診断createのみ許可することを確認する。RulesのallowはORなので包括的allowを残してはいけない。
3. 管理者UID、サーバー資格情報を設定。本番公開・ルール変更は別途承認を得て、保護ルールとアプリを調整して適用する。移行中の旧adminは指定した既存管理者UIDのみ直読みを許可する。
4. 管理者で全期間累計と上表の月別数を再照合し、集計生成時間と更新後のログを確認する。実データ件数は公開時に変化しうる。
5. 旧画面の利用期間を経て `firebase/firestore.rules` の全面クライアント拒否へ移行する。切替後の旧画面は保存に失敗するので再読み込みを案内する。新画面は未送信キューから同じUUIDで再送する。
6. 管理者外の401/403、通常診断の新規保存・同一再送、共有/履歴で新規保存されないことを確認する。

未送信キューは既存localStorageに保存し、全サイト再訪問・onlineイベント・手動操作で再送する。ブラウザデータ消去やlocalStorageの利用不能では永続性を保証できない。旧保存方式で過去に失敗した結果は復元しない。

ロールバックは原本を削除せず、アプリと対応する制限付きルールを整合させて戻す。包括的な匿名write許可へ戻さない。診断結果や既存の注文コレクションへの移行・削除は不要。

## 検証用プレビュー

`npx vite --config tests/admin-browser/vite.config.ts` で http://127.0.0.1:3004/ を起動する。認証とAPIを合成データに置換した検証用で、本番データではない。Next.jsの公開ルートには含めない。`?period=YYYY-MM`、`?period=all`、`?stale=1` で期間別・全期間・古い集計の表示を確認できる。

デザインは既存のPrismaトークンを維持（白いカード、slate-50背景、prisma系ティール、青/緑/紫のKPIアイコン）。ダッシュボードスキルは情報階層・比較範囲・分母・表/CSV代替・状態表示に適用。強調色だけで意味を伝えない。公式ガイドの影を避ける推奨に対しては、既存デザインを維持するユーザー指示を優先し、既存と同じ弱い影のみを使う。

確認済み：1280px、768px、390pxで全体の横はみ出しなし。月入力、全期間切替、数値表、50件追加取得を合成データで確認。実集計関数による本番読み取り照合で572件、9月68件、月別合計572件。月指定ログクエリは既存インデックスで51件取得成功。ローカル本番ビルドの未認証APIは401、空の診断送信は400。いずれも本番への保存・キャッシュ生成は実施していない。

GitHubのPRISMA_ADMIN_UIDS変数を設定済み。mainへのpushで型検査・テスト・ビルド後に既存VPSへ自動反映する。ルールはEmulatorではなくFirebase Rules APIで検証済み。

未確認：実ブラウザでの新保存APIへの正常保存、本番公開後の表示。複数利用者の受入・全アクセシビリティ基準への適合は未評価。

最終自動検証：`npx tsc -p tsconfig.app.json --noEmit` 成功、`npx vitest run` 19ファイル・326件成功、`npx next build` 全1,686静的ページ生成成功。既存の型検査を妨げていた未使用import/type-only importと、削除済み定数を参照していた価格テストを最小限修正した（価格計算や課金処理は変更していない）。
